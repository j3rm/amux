# Server-Loss Recovery

The authoritative Jeremy-facing recovery playbook lives in **Notion**,
maintained by **Cypra**. This wiki page is the machine/agent-side pointer:
where things live, what changes, and — most importantly — **when to remind
Cypra to update the Notion page**.

## The two documents

| Document | Owner | Audience | Purpose |
|---|---|---|---|
| **[Notion: AMUX — Server Loss Recovery Playbook](https://app.notion.com/p/AMUX-Server-Loss-Recovery-Playbook-3d8e67713ec681e3a097c915c5120e22)** (id `3d8e6771-3ec6-81e3-a097-c915c5120e22`, filed under **Infrastructure**) | Cypra | Jeremy (human) | Order-of-ops, credential locations, who to contact, phone tree. What Jeremy actually does when the VM is gone. |
| **`amux-config/README.md`** (auto-generated by `amux-backup.sh`) | amux-helper | Restore agent | Machine-side deep detail: prerequisites, restore steps 1-8, systemd units, what the backup does/doesn't include. |
| **`backup/restore-verify.sh`** | amux-helper | Restore agent | Automated punch list after restore — DB tables, SSH perms, TLS validity, working dirs, etc. |

The Notion page is the entry point. It references `amux-config/README.md`
for the machine-side steps and `restore-verify.sh` as the after-restore check.

Cypra also keeps a working draft as amux note `amux-server-loss-recovery-playbook-draft`
— that's the copy she edits between Notion pushes. Ping her on the board for
future updates; don't try to edit the Notion page directly (only Cypra has the
Notion write path).

## What's backed up

Run every 6h by SCHED-39 to `git@github.com:j3rm/amux-config.git` (private).
Full inventory of what's included and what's deliberately excluded lives
in the auto-generated `README.md` at the root of that repo.

Summary:

- **In:** SQLite `.dump`, all session `.env`s, agent notes, per-project MEMORY.md,
  channel history, org container specs + per-org SSH secrets, TLS cert, host CLAUDE.md,
  systemd units, Jeremy-personal Gmail OAuth.
- **Out (deliberate):** conversation `.jsonl` transcripts (~1GB, per-run),
  per-container HOMEs (~16GB, containers re-`/login`), server logs, uploads,
  the `agent-skills` git repo (synced separately).

## Doc-sync trigger — WHEN to ping Cypra

Any change to ANY of the following requires a board item to Cypra
requesting a Notion update:

- What `amux-backup.sh` includes or excludes (the "What this backup contains"
  and "What this backup does NOT contain" sections in its README).
- Any restore-step in `amux-backup.sh`'s README (steps 1-8).
- Prerequisites on a fresh VM (Ubuntu version, apt packages, npm globals).
- Systemd unit names or paths.
- The known-gaps list (repos without remotes, unpushed work heuristics).
- Off-site backup destinations (currently: GitHub only via `AMUX_BACKUP_REPO`).
- `restore-verify.sh` — new checks, new failure modes, or renamed items.

**Board template for the Cypra update ping:**

```
title: Update Notion Server-Loss Recovery Playbook — <what changed>
session: Cypra
creator: <your-session>
desc: |
  Recovery-playbook-affecting change shipped in commit <sha>. Notion doc
  needs the following updated:
  - <bullet: what changed>
  - <bullet: implication for Jeremy's recovery sequence>

  Reference: amux repo at commit <sha>, files:
  - backup/amux-backup.sh
  - backup/restore-verify.sh (if applicable)
  - wiki/Server-Loss-Recovery.md
```
